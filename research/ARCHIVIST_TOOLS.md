# Open-source tools for archival disc-image workflows

Reviewed September 30, 2026. This is a curated catalog of 18 tools, not an exhaustive inventory or a comparative installation test. Capabilities come from project-owned documentation; judgments about suitability are our assessment. Machine-readable versions: [CSV](archivist-tools.csv) and [JSON](archivist-tools.json), including activity snapshots, license links, and evidence levels.

## Recommendation

Keep Disc Straighten as the specialized image-preparation command. No complete substitute was verified among the tools reviewed for **weak physical rim detection despite shifted printing + independent spindle detection + perspective rectification + mixed-direction text consensus + feathered annular alpha + measured geometry/provenance logs**. This is a bounded search finding, not a claim that no such tool exists anywhere.

Use ScanTailor Advanced/NAPS2 for accompanying paper scans, Tropy for research-photo organization, and an existing Archivematica/Kitodo/Goobi installation for institutional workflows. SIPI is relevant to image delivery, with a material non-open dependency caveat. Documentarist is archival prior art but archived. No cataloged application was installed, copied into our runtime, or benchmarked in this review.

Searches combined optical-disc label/crop/straighten terms with archival photograph, digitization, deskew, perspective, and preservation terms, then followed canonical repositories and licenses. Many “disc imaging” results actually concern reading optical sectors or ISO files. Those preserve disc contents and do not compete with photographing the physical label. One apparent disc-segmentation result, InternDan/EvangelosImageProcessing, proved to be medical imaging and was excluded.

## Implementation candidates

| [libvips](https://github.com/libvips/libvips) · [LGPL-2.1](https://github.com/libvips/libvips/blob/master/LICENSE) | Demand-driven, parallel image processing suited to large collections and memory-conscious pipelines. | No disc-specific decisions. | [imageproc](https://github.com/image-rs/imageproc) · [MIT](https://github.com/image-rs/imageproc/blob/main/LICENSE) | Rust geometric transformations and other image operations. | Inspected warp interpolation choices are nearest, bilinear, bicubic; not a drop-in EWA Lanczos3/color-managed renderer. **Assessment:** Useful Rust building block, but replacing the current renderer would require a separate quality and performance project. |

## License and maintenance findings

These are separate alternatives, **not one license-compatible bundle**. The catalog does not relicense their code. GPL, AGPL, MPL, LGPL, permissive application licenses, and separately licensed dependencies need their own treatment if integrated or redistributed. This release introduces no additional runtime dependency; see [our notices](../THIRD_PARTY_NOTICES.md).

GitHub's license detection is incomplete: unpaper's README explicitly identifies GPL-2.0-only, NAPS2's LICENSE says GPL-2.0-or-later, Tropy's LICENSE says AGPL-3.0, Documentarist has BSD-3-Clause text, and JHOVE specifies LGPL-2.1-or-later. These were read rather than treating null/NOASSERTION API values as permission. A recent repository push can be a dependency or documentation update; it does not prove release quality or maintained platform support. Exact observed dates are in the catalog data.

[Fred's ImageMagick scripts](https://www.fmwconcepts.com/imagemagick/index.php) include relevant unrotate/unperspective utilities, but their published terms restrict commercial use and require permission for redistribution/incorporation. They are excluded from the open-source shortlist and were not adopted. The ImageMagick engine itself has different licensing.

## Archival use of this CLI

Keep the original full-frame capture and its checksum as the preservation source. Store our transparent, rectified image as a documented derivative: background and aperture removal discard capture information, while warping necessarily resamples color. Preserve both JSON logs with it, including review flags, measured source geometry, transform, exact knockout dimensions, and runtime versions. Link both images to one physical-object identifier. A 16-bit export from an 8-bit JPEG is still an 8-bit source capture with interpolated output precision.

Our JSON is application provenance, not an implemented METS/PREMIS export. Institutional integrations, persistent identifiers, a durable human approval record, and calibrated camera/lens metadata are sensible next steps when an actual archival workflow needs them. Current Apple Vision OCR remains a proprietary macOS system dependency even though our application source is MIT. An all-open, cross-platform build needs a separately validated OCR backend.
